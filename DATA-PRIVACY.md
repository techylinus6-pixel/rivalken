# Rivalken player-data disclosure

This document describes what the code in this folder does, and separates that from the Supabase setup that an operator still has to perform. No Supabase project has been created or configured by this project.

## Data handled by the game

- **Nickname:** Players choose a 3–16 character nickname. It is included in the encrypted profile and is sent in plaintext to the Rivalken race server when the player joins a race, because it is shown to other racers. Treat it as a public display name; do not use a real name.
- **Account ID:** Supabase Auth creates a random UUID for each account. It is the only player-profile table identifier.
- **Password:** The browser sends the password directly to Supabase Auth over its HTTPS API. The Rivalken Node server does not receive or store it. Supabase Auth stores its own password-verification data, not the raw password, and controls its handling and retention. The browser also uses the password to derive an encryption key; neither the password nor that key is persisted by this code.
- **Private game profile:** The nickname, credits, level, XP, race/win/podium counts, garage inventory, selected car, paint, customizations, upgrades, and a race-award identifier are JSON-encrypted in the browser with AES-GCM and bound to the player's UUID as authenticated data. The encryption key is derived from the password and a random salt using PBKDF2-SHA-256. A fresh AES-GCM IV is used for each saved update.
- **Race data:** While racing, the game server receives the chosen nickname, selected car, its appearance and upgrades, and normal live driving state (position, speed, controls, fuel). Other connected racers see the nickname, car, and race standings. The game server does not receive the full saved profile or its career statistics from the profile database.
- **Display settings:** Reduced-motion and high-contrast preferences are stored in browser `localStorage`. The Supabase client is configured not to persist an auth session in browser storage.
- **No requested contact details:** The game form does not ask for a real email address, real name, or phone number. Supabase Auth's email/password interface is used with a synthetic login identifier of the form `SHA-256(lowercase nickname)@players.rivalken.invalid`; this is not a deliverable email address. Supabase Auth stores that identifier and the account UUID. Because nicknames are short, the hashed identifier is not guaranteed to conceal a guessable nickname from a project owner.

## Where data goes and who can access it

When configured, the browser connects directly to the configured Supabase project using its public anon/publishable key. Supabase Auth handles account credentials. The `public.player_profiles` table stores only the Supabase UUID, encrypted profile text, encryption salt, IV, and crypto version. The migration enables Row Level Security and permits an authenticated user to select, insert, or update only the row whose `player_id` equals `auth.uid()`. There is no public leaderboard endpoint; public career rankings are disabled.

The Rivalken Node server serves the game, relays live race state, and awards race results to the browser. It no longer reads or writes `data/accounts.json`, handles account passwords, or stores Supabase service credentials. It does not write connecting IP addresses to an application database or log them in its request handlers; the operating system, network operator, and any hosting provider can still observe network connections and IP addresses. Supabase may separately process authentication, abuse-prevention, and service telemetry under its own policies. The previous local-auth version held IP-based failed-login counters in memory for up to 15 minutes and session tokens in memory; those mechanisms are removed. A stale `apex_session` cookie is cleared the next time the browser contacts this server. The current Supabase SDK session is held in page memory only and is not restored after a reload. Authentication/encryption requires a secure browser context: `localhost` or HTTPS. The app blocks account creation/sign-in from ordinary LAN HTTP origins; the built-in server itself does not provide TLS.

The game server sends a restrictive Content Security Policy, disables framing and MIME sniffing, limits browser permissions, and sets `Referrer-Policy: no-referrer`. The policy allows game assets from this server, multiplayer WebSockets on the current host, and the configured HTTPS Supabase project. These browser controls complement HTTPS; they do not encrypt ordinary HTTP traffic from other devices on a LAN.

Encryption is a best-effort privacy barrier, not a promise that the project owner cannot learn player data. A Supabase project owner can inspect Auth account metadata (including the synthetic identifier and UUID), change the delivered game code to capture future passwords or plaintext, and access/modify backend configuration. The project owner can also view ciphertext and metadata in the profile table. RLS protects player access through the normal client API; it does not prevent project owners or privileged Supabase operators from bypassing RLS. The client also awards in-game progress, so a modified client can falsify its own profile.

## Account recovery and deletion

The synthetic identifier cannot receive email. There is no password reset or recovery route. The password is also required to derive the profile key; if it is forgotten, this implementation cannot decrypt the saved profile. There is no password-change flow.

The game includes a **Delete account** control, and this folder includes a `delete-account` Supabase Edge Function. Once that function is deployed with its required secrets, it verifies the caller's Supabase access token and deletes that Auth user; the profile row is removed by its foreign-key cascade. The service-role key is read only from the Edge Function environment and is not included in browser code or the Node server. Until the function is deployed and configured, deletion is not live and the control will report an error. Deleting the project account does not guarantee immediate removal from provider backups, security logs, or other retention systems; consult Supabase's current data-retention terms.

## Local and legacy data

At the user's request, the old `data/accounts.json` file was deleted. The previous version used it for usernames, salted password hashes, and plaintext game profiles. This removes that file from the project folder, but cannot remove copies made elsewhere, filesystem backups, or snapshots. The old local saves are lost; no migration is available.

## Setup status and free-tier limits

The implementation is scaffolded but not connected to a live Supabase project. To activate it, an operator must create/configure a Supabase project, set `SUPABASE_URL` and its public anon/publishable key in a local `.env`, apply `supabase/migrations/20261120000000_private_player_profiles.sql`, turn off email confirmation for the synthetic non-deliverable login identifier, deploy `supabase/functions/delete-account`, and set the service-role key as an Edge Function secret. Never put the service-role key in `.env`, browser code, or a committed file. `.env.example` contains placeholders only.

No paid Supabase plan, deployment, or project has been created by this code change. Supabase Free has quotas and availability limits that can change; free projects may be paused for inactivity, and Auth, database, and Edge Function usage is subject to the current plan limits. Check Supabase's current plan terms before relying on long-term availability. Nothing in this repository automatically upgrades a plan or incurs a Supabase charge.

This project previously loaded Google Fonts from Google servers. Those remote font requests have been removed; the game uses local/system fallback fonts instead. A scan of source/configuration files outside `node_modules` found no hardcoded credential-like key/token signatures or email-like contact strings. Numeric "phone-like" pattern matches were in game geometry, artwork, CSS, or the documented local port; they are not contact fields. No local `.env` file was present during the scan. The deleted legacy account file was not inspected before deletion; separate backups or copies may still contain old account data.
